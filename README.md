# mesh-network-tools

Инструменты на ПК для прошивок meshcore. Сейчас здесь проверки (`selftest.py`); это же место
для будущих инструментов вроде разбора логов и редактора карт.

Репозитории рабочего дерева лежат рядом друг с другом — так их собирает PlatformIO
(`symlink://../mesh-network-core` в `platformio.ini` прошивок), и так же они ищут друг друга
здесь:

```
Repos/esp32/
├── mesh-network-core/     ядро протокола
├── mesh-network-tools/    ← этот репозиторий
├── meshcore-fork/         прошивки Heltec
└── tdeck/                 прошивка LilyGO T-Deck
```

## Проверки

Идут на обычном компьютере, железо не нужно. Что они делают:

- вырезают из исходников **настоящие** функции (CRC, `jsonEscape`, `buildPingReply`,
  `rawBuildFrame`, `floodGapMs`, `maybeQueueRelay`), собирают их хостовым `g++` с
  `-fsanitize=address,undefined` и гоняют на граничных данных — так ловятся переполнения
  буферов, которые на плате проявились бы падением;
- сверяют связи, которые расходятся молча: тайминги против худшего случая в эфире, разметку
  страницы координатора против её скрипта и против маршрутов сервера, признаки сборки против
  того, что читает ядро;
- проверяют форматы, которые читает устройство: маркер платы в образе, `.otaz`, пакет `.tapp`,
  шапку ELF загрузчика приложений.

### Запуск

```
python3 selftest.py --target fork      прошивки Heltec (meshcore-fork)
python3 selftest.py --target tdeck     прошивка T-Deck
python3 selftest.py --target core      только ядро протокола
python3 selftest.py --target all       все цели подряд
```

Привычные команды из каталога прошивки продолжают работать — там лежит обёртка на три строки:

```
cd ../meshcore-fork && python3 scripts/selftest.py
cd ../tdeck         && python3 scripts/selftest.py
```

Пути по умолчанию — соседние каталоги; перебиваются ключами `--root`, `--core` и
переменными `MESHCORE_ROOT`, `MESHCORE_CORE`. Обёртки находят этот репозиторий по
`MESHCORE_TOOLS` либо рядом с собой.

Нужен `g++`. `node` по желанию: без него пропускается проверка синтаксиса страницы.

### Как это устроено

| Файл | Что в нём |
|---|---|
| `selftest.py` | запускатель: разбирает `--target`, ищет репозитории, печатает итог |
| `mcselftest/harness.py` | обвязка: пути (`Ctx`), вырезание функций из исходников, сборка на хосте |
| `mcselftest/cshims.py` | заглушки Arduino (`random`, `String`) для хостовых сборок |
| `mcselftest/targets.py` | цели: какой набор проверок прогнать для какой прошивки |
| `mcselftest/suite_core.py` | проверки ядра — идут для **любой** цели |
| `mcselftest/suite_fork.py` | своё у meshcore-fork: страница, кнопки в MQTT, приложение |
| `mcselftest/suite_tdeck.py` | своё у T-Deck: пакет `.tapp`, шапка ELF |
| `mcselftest/suite_font.py` | шрифты T-Deck: кириллица в пропорциональных шрифтах |
| `mcselftest/suite_meta.py` | проверки самого набора проверок (см. ниже) |

Проверки ядра идут для любой цели намеренно. Раньше они лежали в `scripts/selftest.py`
каждой прошивки, то есть ядро проверялось из потребителя, и наборы разошлись: у
`meshcore-fork` их было 25, у `tdeck` — 8, хотя ядро они возят одно и то же. Теперь у T-Deck
их столько же, сколько у форка.

Часть проверок кросс-репозиторные — например, «ни один `features.h` не переопределяет
`FEATURE_RELAY`» смотрит сразу в обе прошивки. Внутри одной из них такую проверку и не
получилось бы держать.

### Добавить проверку

1. Напишите функцию `<имя>_test(ctx)` в подходящем наборе: про ядро — в `suite_core.py`,
   про конкретную прошивку — в её `suite_*.py`.
2. Допишите вызов в `mcselftest/targets.py`.
3. **Сломайте свою правку и убедитесь, что проверка упала.** Если после отката она всё ещё
   зелёная — она ничего не проверяет.

Шаг 2 забыть нельзя: `suite_meta.wiring_test` сверяет, что каждая написанная проверка
кем-то вызывается, и падает на осиротевшей. Это и есть плата за переезд проверок из того
файла, где они вызывались строкой ниже.

### Добавить прошивку

Запись в `TARGETS` в `mcselftest/targets.py` и, если у неё есть свои проверки, модуль
`suite_<имя>.py` рядом. Больше нигде ничего трогать не нужно.

## Версии

Каждая прошивка объявляет в `tools.ref`, какую версию проверок считает штатной для своей
ветки, — так же, как `core.ref` объявляет версию ядра. CI берёт проверки именно по этому
значению, а не «что сейчас в main»: иначе правка проверок красила бы чужие ветки.
